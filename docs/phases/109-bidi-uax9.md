# Phase 109 — bidi: Hebrew and Arabic are reordered, not mirrored

## What was wrong

Every text run in this engine was placed left to right. The inline formatting
context walked the logical order of the text, measured each word, and put the
next one to the right of the last. For Latin script that is the answer. For
Hebrew it is not: `שלום` was painted with its first letter on the left, which
reads backwards, and a line that mixes scripts had its runs in the wrong order
as well as its words inside out. `(שלום)` came out with its brackets where the
logical string put them.

Arabic had the same problem, and one more that this phase does not fix:
without shaping, its letters are drawn unjoined (`ROADMAP.md` Tier 1 #2).

There was no bidi pass anywhere in the tree. `direction` and `unicode-bidi`
were not CSS properties the style system knew, `grep -rn bidi src/` found the
IDNA table and nothing else, and no code point in the layout path ever asked
what script it belonged to. `ROADMAP.md` listed this as Tier 1 #3 — *"Arabic and
Hebrew come out reversed"* — and the Open tasks table had no row for it.

## What changed

**`include/litebird/text/Bidi.hpp`, `src/text/Bidi.cpp`** — the Unicode
Bidirectional Algorithm, rules P2 to L2, for one paragraph at a time:

- P2/P3: the paragraph level is the direction of the first strong character,
  with the text between an isolate initiator and its matching PDI skipped.
- X1 to X8: the explicit levels — `RLE`, `LRE`, `RLO`, `LRO`, `PDF`, `RLI`,
  `LRI`, `FSI`, `PDI` — on a directional status stack of depth 125, with the
  overflow counters UAX #9 asks for. X9 removes the embedding characters.
- X10: isolating run sequences, built from level runs chained through
  isolate initiators and their matching PDIs, each with its own `sos`/`eos`.
- W1–W7, N0–N2 (bracket pairs by BD16, with the 63-deep stack limit), I1–I2.
- L1 for the paragraph, and L2 for a line; `bidi_mirror` is L4's pair.

**`include/litebird/text/BidiTables.hpp`, `src/text/BidiTables.cpp`** — the
tables, generated by `tools/gen_bidi_tables.py` from Unicode 17.0.0: 1,267
Bidi_Class ranges (with the `@missing` defaults written out, so an unassigned
code point answers without a second pass), 128 bracket pairs, 428 mirror
pairs. Same provenance and version as the tree's other Unicode tables — the
generator reads `unicode-org/unicodetools` at `unicodetools/data/ucd/17.0.0/`,
and `unicode-org/icu` `release-78.2` for the conformance suites.

**`src/layout/LayoutBox.cpp`** — after a line's fragments have their absolute
positions, `apply_bidi_to_line` runs the paragraph pass over the line's own
text (a non-text inline contributes U+FFFC, as CSS 2.1 asks). If no character
resolves to an odd level the function returns without touching anything, which
is why every Latin page lays out exactly as it did. Otherwise it cuts each
fragment at a change of level, reorders the pieces by rule L2, gives them the
line's width back in the same proportion, and rewrites the text of each
odd-level piece **backwards and mirrored** — the painter draws a run left to
right, so an RTL run has to be handed to it in visual order.

**`tools/conformance/bidi_check.cpp`**, **`make bidi-conformance`**,
**`tests/bidi/`** — the scoreboard. Both Unicode suites, vendored gzipped
(1.3 MB + 0.4 MB; `tests/bidi/README.md` records the URL, the tag and the
checksums), ungzipped into `build/bidi/` and run against the algorithm alone —
no engine, no DOM, no network.

## How it was verified

```
$ make bidi-conformance
BidiTest (Bidi_Class sequences):            770241/770241 (100.0%)
BidiCharacterTest (code points, brackets):   91707/91707 (100.0%)
Bidi conformance, total: 861948/861948 (100.0%)
```

Two seconds, on the whole of both suites: 770,241 cases of Bidi_Class
sequences (each line run under every paragraph direction its bitset allows)
and 91,707 cases of real code points, which is where bracket pairs, mirroring
and the class table itself are exercised.

`make test` grew a suite, `bidi_reorders_hebrew_and_arabic_runs`, which asserts
the levels and visual order of five paragraphs and then asserts what the layout
paints for three of them: two Hebrew fragments in the order the eye reads them,
each written backwards; a Latin line untouched; `(שלום)` with the glyphs
mirrored. `make test` → **268 / 268**.

The rest of the tree is unchanged: `make conformance` 1973/1973,
`make diff-trees` 6,000/6,000 corrected parse5, `make wpt` 9567/9824 with no
unlisted failure, `make js-conformance` 1141/1158, `make dom-conformance`
678/678, `make url-conformance` 1188/1188, `make xml-conformance` 1718/1718.

Four bugs found by the conformance run, each a rule's exact wording:
`RLE`/`LRE` push a **neutral** override status (only `RLO`/`LRO` push one);
W2 and W7 look for the first *strong* type, and a number is not one; `sos`/`eos`
and N2 take the levels the **X rules** assigned, not ones I1/I2 have already
raised in an earlier sequence of the same paragraph; and BD16 pairs only
brackets that are still `ON`, so an override is not undone by N0. The last
case in the suite is 64 nested parentheses: UAX #9 caps the bracket stack at
63, and past that this implementation drops every pair in the sequence, which
is what the suite's expected levels say.

## What is still open

- **`direction` and `unicode-bidi` are not CSS properties here.** The paragraph
  level comes from P2/P3 alone, so a `dir="rtl"` block does not start
  right-to-left unless its first strong character is RTL. `<bdi>` and
  `unicode-bidi: isolate` are inert.
- **No shaping.** Arabic letters are ordered correctly now and still unjoined;
  that is Tier 1 #2 (`GSUB` contextual lookups), not this phase.
- **L3 is not done**: a combining mark on an RTL character is positioned by the
  painter's advance, not attached.
- **Every RTL page pays for a paragraph pass per line box**, and a line that
  contains an RTL character is re-measured in pieces; a purely Latin line
  returns before measuring anything.
- **`box->lines`, the text a `TextNode` reports for inspection, is in visual
  order** on an RTL line, because the fragments were reordered in place.
