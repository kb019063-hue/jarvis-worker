# URL conformance corpus

The URL tests of the [web-platform-tests](https://github.com/web-platform-tests/wpt)
project, which is what browsers test their URL parsers with:

| File | From `url/resources/` at commit | What it holds |
| :--- | :--- | :--- |
| `urltestdata.json` | `065d99ab62bf0b6ca04907f423625801c350edb2` (2026-11-12) | An input, a base and either every part of the URL they make or `"failure": true` |
| `setters_tests.json` | `dca32277cbf3d40b3ec20bba999a987b0ea51ed7` (2026-11-13) | A URL, a part, a value assigned to it and the parts expected afterwards |

The files are copied unchanged; `LICENSE.md` is the project's licence
(3-Clause BSD).

## Running it

```
make url-conformance
python3 tools/conformance/run_url_conformance.py --show 20
```

The runner writes one script that holds both files, runs it with
`litebird --run-script` and reads the result. A parsing case passes when
`new URL(input, base)` gives every expected part (`href`, `protocol`,
`username`, `password`, `host`, `hostname`, `port`, `pathname`, `search`,
`hash`, and `origin` and `searchParams` when the case names them), or throws a
`TypeError` and `URL.canParse` says no when the case expects a failure. A
setter case passes when assigning the value leaves every expected part.

## Status

All 1,188 cases pass, and `make url-conformance` enforces a floor of 1,188.

Host names with characters outside ASCII are converted with Unicode's
UTS #46 (Nontransitional Processing, the algorithm the URL Standard's
domain parser points at): each code point is mapped (case folding and
compatibility mappings), the result is normalised to NFC, and each label is
validated — no leading combining mark, the ContextJ rule for
ZWNJ/ZWJ, the bidirectional rule (RFC 5893) when the domain is a bidi
domain name — then Punycode-encoded if it still holds non-ASCII
(`http://faß.example` becomes `http://xn--fa-hia.example/`). The implementation
is `src/net/Idna.cpp`; the mapping, decomposition, composition, bidi and
joining-type tables are generated by `tools/gen_idna_tables.py` (mapping and
joining types: Unicode 15.1.0 from the `idna` package; marks, combining
classes, decompositions, composition pairs and bidi classes: the generator
host's `unicodedata`, Unicode 14.0.0 here — the drift only affects code
points assigned after Unicode 14) into `src/net/IdnaTables.cpp`.

How it was verified: every Unicode code point was run through
`domain_to_ascii` and compared byte-for-byte against Node's `domainToASCII`
(1,112,063 inputs, 99.9% identical) plus a 2,263-case sweep of code-point
pairs and multi-code-point sequences checked against both Node and Python's
`idna` (UTS #46). Every divergence found is accounted for:

- ẞ (U+1E9E): litebird keeps the UTS #46 Nontransitional answer, `xn--zca`.
  Node's ICU maps it to `ss`; the WHATWG and the corpus win, and the
  divergence is deliberate.
- Labels mixing left-to-right and right-to-left characters (e.g. `aא`) and
  labels whose first code point is an AN-class digit or a combining mark:
  litebird rejects them, as the URL Standard's CheckBidi and UTS #46 require
  (Node is lenient here). Pure RTL labels such as `http://א/` parse.
- Code points that are PVALID only because they are unassigned in Unicode
  (e.g. U+11F00): accepted. Node/ICU rejects them for lack of bidi data;
  UTS #46 does not reject them (they are not R/AL/AN and not leading marks).
- Super- and subscript digits (`²`, `₀`, `¹²`) map to ASCII digits, so
  `http://²/` is the IPv4 address `0.0.0.2` — the IPv4 fallback lives in the
  host parser, which is also why Node's `domainToASCII` (which embeds IPv4
  handling) reports different strings for the digit cases but the same final
  hosts.

Empty labels pass through when `VerifyDnsLength` is off (`http://a./` is a
rooted host, per UTS #46 "the empty root label is passed through"); the
strict mode used for validation-error reporting keeps them disallowed.
