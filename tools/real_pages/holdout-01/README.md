# Holdout 01 · Four unfamiliar browsing tasks

**First exposure only.** On the local `771fb6f` engine build that completed v1's 20 tasks, Chromium completed **4/4** holdout tasks. Litebird passed **0/4 automated gates**. On review, **1/4 user actions visibly completed**, with a measurable API/layout defect, and three did not. Neither figure is a measure of general web compatibility. Do not add this denominator to v1's.

[Side-by-side PDF](results/holdout.pdf) · [frozen manifest](manifest.json) · [native traces](results/litebird.json) · [Chromium traces](results/reference.json) · [frame review](results/review.json).

| Task | Native observation | Strict verdict |
|---|---|---|
| Rust Book: Getting Started → Installation | The source heading rendered. Two Next chapter links were found, with boxes 760×0 and 0×0. No viewport click could be sent to their centers; the page stayed at Getting Started. | Blocked, not a navigation pass. |
| W3C APG: first tab → Carl Andersen with ArrowRight | Tab 2 had focus and selection, tab 1 lost selection, and the biography is readable in the after frame. The JS rectangle reports its top at y≈2061 in a 600px viewport, with `window.scrollY` 0. The screenshot contradicts the failed geometry assertion. The tabs also stack vertically, and the page logs a syntax error at `import`. | User action completed; **not** a clean automated or visual pass. |
| MDN: open and cancel a modal | The open flag and `animalNotChosen` return value changed, but the form was visible before opening and after canceling. No visible modal/backdrop; focus stayed on Cancel instead of returning to Update details. | Incomplete. A return value alone is insufficient. |
| TodoMVC ES5: add and complete Buy mangoes | Enter added one correctly named item and cleared the input. The toggle's center hit a label rather than the checkbox; the driver did not click a different target. One item remained. A script also reported an unsupported `with` statement. | Add passed; complete did not. No full-task pass. |

**Pixels.** Zero tolerance on 800×600 RGBA post-action frames. None of the four raw pairs matches. Only the tabs reached a comparable end state: that pair is a visual failure. The other three pairs document different outcomes; their pixel counts are not rendering scores. The dialog report also shows the open intermediate state.

Off-origin requests are blocked in both browsers; this is not a test of the live deployed pages. The task set is now exposed: future fixes on it are regressions/improvements against a known set, **not** another unseen test.

**Reproduce on Linux.** From repository root, use the engine revision above (not an arbitrary newer `main`) and a fresh scratch directory. Follow the v1 [Chromium dependency setup](../README.md#rerun-on-linux-from-repository-root) for `NODE_PATH`, the browser package and `LD_LIBRARY_PATH`. `capture.py` uses `gh api` and codeload for the pinned static files, and verifies TodoMVC's two runtime packages against its upstream lockfile. It never installs/runs upstream package scripts.

```sh
H=tools/real_pages/holdout-01; R=$(mktemp -d)
python3 "$H/capture.py" "$R/sites"
node "$H/oracle.cjs" "$R/sites" "$R/run"
make -j2 build/litebird
g++ -std=c++20 -Iinclude "$H/drive.cpp" $(find build -mindepth 2 -name '*.o') -o "$R/driver"
python3 "$H/run.py" "$R/sites" "$R/run" "$R/driver"
```

Read **all** rows (the runner records nonpasses rather than stopping at the first one). Native: fresh process per task, sockets denied, 45s wall budget, real shell clicks/keys, read-only JS observations. Reference: fresh context per task, same local origin/files, real mouse and keyboard. Initial and final screenshots, plus the open dialog and added todo, are in the run directory. Focus and visible result are separate checks; inspect the screenshots instead of trusting rectangles alone.

## Re-run on `main` `a76e893` (Vellum, 2026-11-23)

[Re-run outcomes](results-rerun06/litebird.json) · [frozen reference re-validated 4/4 by a fresh Chromium run the same day](results-rerun06/reference.json) ([fresh oracle frames committed](results-rerun06/oracle-frames/), HeadlessChrome/131.0.6778.0) · [frame review with before/after pixel counts](results-rerun06/review.json) · [native logs](results-rerun06/H1.log).

Same frozen snapshots, same tasks, same gates, same driver — no engine change of any kind in this re-run. The dialog phases landed after the first exposure (`771fb6f`): #220 (a dialog takes the focus it opens with), #183 (default `open` rendering honored), #230 (a modal keeps the page out of reach), #233 (a modal paints in the top layer). The re-run measures what they bought on these four unfamiliar tasks, and nothing else.

**Litebird now passes 1 of 4 automated gates — H3 (MDN dialog), up from 0/4.** Chromium still passes 4/4. This is one scenario, not a web-compat claim.

| Task | First exposure | Now | Gate result |
|---|---|---|---|
| H1 · Rust Book, Next chapter | 0 boxes usable (760×0, 0×0), blocked | Same family of failure, root cause now isolated in the source: the anchor's only content is `<i class="fa fa-angle-right"></i>` and `.fa-angle-right:before{content:"\f105"}` — Litebird parses pseudo-elements but never matches them (`src/css/StyleResolver.cpp:859` returns false on `has_pseudo_element`) and generates no content, so the anchor is a zero-content inline box: no ink, no hit target | Blocked, not a navigation pass |
| H2 · APG automatic tabs | Geometry assertion failed (top ≈ 2061), blocked | Gate still fails on the same assertion: `getBoundingClientRect().top` reads **2061.4 in a 600px viewport** while the after frame shows the biography at y≈560 (width 736, height 100, visibility `visible`, `scrollY` 0). Tab focus, ARIA selection and panel hiding all work; `#tabpanel-1` computes `display: block`→hidden correctly per the hidden() check. Also logged: `Uncaught SyntaxError: Unexpected token 'import' (line 52)` — `await import('./specLinks.mjs')` in `shared/js/app.js` (dynamic `import()` is open, as ROADMAP says); it kills the spec-link enhancement in app.js, not the tabs (`tabs-automatic.js` is a classic script and works). Do not remove the geometry assertion: it is the assertion catching a real DOMRect defect | Blocked on geometry; biography visibly displayed |
| H3 · MDN modal dialog | 0 gates passed; focus not restored | **Gates pass**: `showModal()` opens, open flag reads true, `Cancel` closes, `returnValue` is `animalNotChosen`, focus returns to `Update details` (focus ring visible in the after frame; before/after differ by 2,836 pixels — near-identical). Frames show what the gates cannot see: the **open state paints no modal chrome** — dialog content flush top-left on a gray canvas, no border, no centering, no padding, and the native `<select>` renders nothing. The closing behavior improved; the opening presentation did not |
| H4 · TodoMVC, add and complete | Added item; toggle hit a label; `with` unsupported | Unchanged in kind. The item is added and shown (`Buy mangoes`, "1 item left"), so model/store/view run despite `Uncaught SyntaxError: 'with' statements are not supported (line 4)` — thrown by the *generated* template source TodoMVC compiles at runtime (`todomvc-common/base.js`: `with(obj||{}){…}`), logged but not gate-fatal. Gate-fatal: at the toggle's center (145,248) the hit-test lands on the `<label>` next to the checkbox, and the driver refuses a non-matching target — the same label-activation gap as at first exposure: Litebird does not route a click on a `<label>` to its labeled control. Painted defects in the item row: the toggle renders as a small box showing `on`, and "1 item left" wraps into a too-narrow column | Add passes; complete does not |

**Pixel comparison** (RGBA, 800×600, vs the same-day fresh Chromium; consult `results-rerun06/review.json`): H1 46,759 → 199,651 (different end state), H2 89,560 → 239,229 (equivalent task outcome, non-identical), H3 2,389 → 36,424 on the open frame but only 2,836 on the after frame, H4 114,815 → 135,510. H2 settled slightly closer to Chromium than at first exposure (259,542); nothing else is comparable.

**What this re-run isolates as engine gaps, smallest first:** (1) label→control activation behavior (H4's gate-fatal step; also why "the toggle's center hit a label" was unusable); (2) `::before`/`::after` generated content — absent entirely, which dead-ends every icon-font-only control on the real web (H1; `StyleResolver.cpp:859`); (3) the `DOMRect`/geometry path disagreeing with the painted layout by ~1,500px (H2; the assertion firing is the engine's fault, not the assertion's); (4) dynamic `import()` not parsing (H2's logged SyntaxError); (5) dialog UA chrome: closed/open rendering honored, but no box, no `::backdrop` layer visible as a distinct layer, no top-layer centering in the open frame, and a native `<select>` paints nothing (H3-open); (6) TodoMVC's runtime-compiled template needs `with` (H4; its absence is logged-but-survivable); (7) checkbox default painting shows the literal string `on`, not a glyph (H4-added). None of these is fixed here: this pull request is measurement and documents only. The first three map to claims an agent can take; (5) needs its own claim on the dialog UA style; (6) and (7) are smaller.

**Honesty notes.** Gates passing on H3 does not mean the dialog *looks* right — the open frame is the visual failure mode, the close/focus behavior is the pass. H2's biography is *visibly* correct in Litebird's frame; the gate failure is a DOMRect defect and the pixels are closer to Chromium than before, so a future fix must move the DOMRect, not touch the assertion. And this set remains exposed: its numbers are regression/improvement measurements, not an unseen sample.
